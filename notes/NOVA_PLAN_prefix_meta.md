## 1. What this tests, and what the simulator already says

Simulator (branch `pilot/prefix-meta`, commit 8e71275; results summarized in `notes/LOG.md`, 2026-10-21 entry, REFRAME): λ_miss = 0.0474 sessions/s, λ_cap = 0.1156, R = λ_cap/λ_miss = 2.44. A 200-session burst at 2×λ_miss left FCFS, LPM-128 and aging-LPM at hit rate 0.000 over [t_b+10k, t_b+25k] in 5/5 seeds; pure LPM 0.198; a length-biased session cap 0.896. Bursts of 25 recovered, bursts of ≥100 trapped every work-conserving policy. Sim reading: **admission, not ordering, drives the trap**, so "LPM-128 inherits the trap" was vacuous there (LPM was trapped too). Sim limits (LOG.md): whole-session KV, no partial radix prefixes, no waiting-prefix refresh, no lazy block eviction.

The real-engine question: does the sim's mechanism (burst → queue → idle KV evicted before the next turn is admitted → all-miss → no recovery) appear on a shipped engine at all? Cells:

| Cell | Engine / policy | Waiting-prefix refresh | Why |
|---|---|---|---|
| A | SGLang v0.5.22 `--schedule-policy fcfs` | on (shipped default) / off | the kill-criterion cell |
| B | SGLang `lpm` (stock, falls back to FCFS above 128 waiting) | on / off | the fallback claim |
| C | SGLang `lpm` with `WAITING_QUEUE_PREFIX_MATCH_MAX` huge (one-line patch, see §6; **not applied**) | n/a (never falls back) | cache-aware ordering without the fallback |
| D | vLLM v0.32.0 `--enable-prefix-caching` (FCFS only) | n/a | second engine |

Refresh facts are from `notes/lit/engine-sources-prefix-cache.md` (raw-file reads by a small model; no line numbers, no SHAs): `SGLANG_ENABLE_WAITING_PREFIX_REFRESH` (EnvBool, default true) bumps LRU recency of the first 128 waiting requests every 32 passes, only for non-cache-aware active policies (FCFS and the LPM fallback). It is a recency bump, not a pin.

Predictions to compare against (from the sim; the kill-test boundaries are now pre-registered from the MEASURED real curve, §4, instead of the simulator's λ multiples): A traps at some λ inside the registered window (λ_miss, min(max μ(n), E0b edge)) if the mechanism transfers; B ≈ A; C is the only cell where ordering could matter, and the sim predicts it does not rescue the system either; refresh off ≤ refresh on in hit rate if the bump helps.

### KV pool: the sim's M is 300k tokens; the real pool is ~3× larger
Qwen2.5-7B KV per token = 2 (K,V) × 28 layers × 4 KV heads × 128 dim × 2 B = 57,344 B (architecture numbers from memory of the HF config; verify in Stage 0). On an 80 GB card at 0.9 utilisation, minus ~15.2 GB weights and a few GB of activations/graphs, that is roughly 1.0M tokens (my arithmetic, not a measurement). The sim used M = 300k. To make the real runs comparable and to keep the metastability reachable with a 200-session burst, the scripts cap the pool at `KV_TOKENS=300000` (`--max-total-tokens` for SGLang; `--num-gpu-blocks-override KV_TOKENS/16` for vLLM, assuming 16-token blocks). Stage 0 must confirm the cap is honored (server log). **A native-pool replicate (`KV_TOKENS=native`, one λ, paired arms) is a REQUIRED item** and is budgeted in §7: a ~3× larger pool shifts the knee n* and the window, so the 300k-token window and `n_cap` do not transfer, and the native pool gets its own Stage-C curve.

### Context length
Max prompt = L0 + 59(Δ+d) = 2000 + 59·650 = 40,350 tokens (the plan-stats output records `max_prompt_tokens`), above Qwen2.5-7B-Instruct's default 32,768. The scripts launch with `CONTEXT_LEN=49152` plus the engines' long-context override env vars (`SGLANG_ALLOW_OVERWRITE_LONGER_CONTEXT_LEN`, `VLLM_ALLOW_LONG_MAX_MODEL_LEN`; names UNVERIFIED). Past 32k the model runs without YaRN; outputs are garbage but ignored (`ignore_eos`, fixed length), and we measure systems behavior only. Alternative if the override fails: `max_turns` 45 (context ≤ 32k), which changes E[T] from 14.76 to ≈14.3 (formula in `effective_mean_turns`) and departs from the sim.

Workload fidelity to the sim: L0 = 2000, Δ = 550, d = 100, geometric mean 15 (cap 60), Exp(5 s) tool time, burst 200 in 60 s. A test checks the prompt at turn t is exactly L0 + (t−1)(Δ+d) tokens and that each prompt extends the previous prompt plus its output.

Known fidelity gaps (all flagged, none hidden):
1. **Output feedback.** In token mode the next prompt appends the model's actual output only if the server returns token ids (`choices.0.token_ids`, or the paths in `server.output_ids_paths`; vLLM may need `request_token_ids: true`, UNVERIFIED). Otherwise it appends synthetic ids (`output_ids_source=synthetic` in every row), so a "hit" covers the previous prompt but not its d output tokens: the follow-up miss tail is Δ+d = 650, not Δ = 550 (tested on the mock). The probe's third request (`return_token_ids=true`, sent regardless of config) shows which case applies (`PROBE_SUMMARY.output_ids_present`). **`output_feedback` is pinned per job** (`OUTPUT_FEEDBACK=server|synthetic`, required for miss/cap/burst; `auto` is for MODE=smoke only) and the analysis guard `output_source_differs` flags compared runs with different sources; see D5. Text mode (`workload.prompt_mode: text`) is the alternative; it appends the returned text but cannot control token counts exactly (no offline tokenizer).
2. **Hit definition.** The sim's hit = whole session KV resident. Here a turn counts as a hit if `cached_tokens / prompt_tokens > 0.5` (reported next to the token-weighted rate). A missing `cached_tokens` is treated as 0 only if some other request in the run reports it (vLLM may omit the field when 0; UNVERIFIED).
3. **Window attribution.** The sim attributes hits to admission time; the client sees completion time (default) or send time. They differ by the service time (seconds vs 1000 s windows).
4. **Queue.** Engine waiting-count metric if present (names UNVERIFIED, candidates in `configs/agentload_analysis.yaml`), else client in-flight count (includes running requests, so it is an upper bound on the waiting queue; `queue_source` column says which). The trap test's backlog quantities are client-side: sessions in the system (arrived minus ended, incl. gate and tool-time sleepers; used for the slope) and the **outstanding backlog** (requests in flight + sessions waiting at the client gate; used for RECOVERED, the analogue of the simulator's waiting queue + gate, but it includes the running requests, up to 256).
5. **First byte.** Streaming is off, so `t_headers` ≈ completion, not TTFT.

### Stage C: closed-population μ(n) on the real engine, cache ON (before E0a/E2)
`MODE=closed`, `configs/agentload_c_closed.yaml`. n ∈ {16, 20, 24, 32, 48, 96, 300} under SGLang `--schedule-policy fcfs` (n = 20 added after the review: the simulator's μ(n) peaks sharply at n = 20-22, and the grid {16, 24, 32} flipped its argmax between 16 and 24 with a 1.6% margin), and n ∈ {48, 300} under `lpm`; one seed per n; **warmup 900 s, measured 1800 s** (2700 s per run); the cache is flushed and verified empty between runs. `N_LIST` has no default (the grid is split over jobs so each fits 4 h: `N_LIST="16 20 24 32"`, `"48 96 300"`, and `POLICY=lpm N_LIST="48 300"`; 4, 3 and 2 runs per job; a 4-run job needs 3.7 h with the job script's own margins). Per run, over the measured window, the analysis (`python -m analysis.summarize closed --run-dirs … --warmup-s 900 [--primary-label LABEL]`) records: **completions/s** (completed sessions/s and the lower-variance turns/s ÷ E[T], both), **hit fraction** (turns with cached share > 0.5; first turns count as misses, so the ceiling is ≈ 1 − 1/E[T] ≈ 0.93), the follow-up-only hit fraction, the **token-weighted cached fraction** (Σcached/Σprompt), the **queue** (engine waiting gauge if the metric exists, else client in-flight requests; `queue_source` says which) and the hardware string. `mu_curve.json` holds per-cell curves, `argmax_n` and the top-level **`n_cap` = argmax μ(n) of the `primary_label` cell** (`mu_max`, `mu_300`, `primary_hardware`), a near-tie flag (`argmax_ambiguous`: runner-up within 5%, one run per n!), whether both estimators agree, and whether the n grid is complete. Ties go to the smaller n. The 300k and the native pool must be summarised SEPARATELY (a note is written if several FCFS cells share a curve). The CAPPED arm reads `n_cap` from this file (`CAP_FILE=…/mu_curve.json` or `N_CAP=<int>`) and the job refuses a file whose `primary_label`/hardware is not its own.

**Known bias (simulator, same protocol; `results/agentload_trap_sim_traces/20261021-070449/transient_bias.csv`).** All n sessions start together at t = 0, so in the window [1000, 3000) of a 35,000 s simulator curve, μ(n) in sessions/s is +65% at n = 300 (a session lives ~6000 s there, longer than the whole run), +18% at n = 100 and 9-25% too LOW at n = 22-30, where μ(n) is also bistable between windows. In prefill-token units the same windows are +13% / +6% / +4-18%. Consequences: μ(300) is only a check (the registered recovery threshold is λ_miss); the argmax `n_cap` and max μ(n) are transient-affected and noisy; staggered session ages would remove the bias and are not implemented (O18).

### E0a: λ_miss (cache disabled in the engine)
`MODE=miss`, SGLang `--disable-radix-cache`, vLLM `--no-enable-prefix-caching`. Closed population 32 (sim: 60, insensitive across 30/60/120), 900 s warmup + 1800 s measured, 3 seeds, plus one population-64 check (analysed separately, not averaged in). Output `calibration.json` with `lambda_miss` (sessions/s, the sim's headline), `lambda_miss_turns_based` (turns/s ÷ E[T]; rates in later configs use it: lower variance for short runs) and **`all_miss_uncached_tokens_per_s`** (prompt tokens/s of the all-miss closed population: the reference of trap criterion (a); `all_miss_cached_frac_tokens_max` must be ≈ 0, else the cache was not off). The E2 jobs pass it as `arrivals.uncached_tokens_ref`. Deviation D2: sim used 5 seeds × 100,000 s.

### E0b: λ_cap from empty (SGLang **FCFS, refresh on**, cache on) — REQUIRED input of the pre-registration
`MODE=cap POLICY=fcfs REFRESH=1` (label `sglang-fcfs-r1`; an LPM bracket says nothing about the FCFS no-burst arm): open loop at multiples of λ_miss, e.g. 1.0, 1.4, 1.8, 2.2, 2.6, 3.0 then a refinement round, one seed per point, 3000 s each, cache flushed and queue drained between runs (`flush_cache` logs success or failure to `job_events.log`; STRICT_FLUSH aborts the job if it fails, because a non-empty cache voids "from empty"). Stability rule = sim's: final queue < 50, fitted queue rise over the last min(5000, run/2) s ≤ 10, not aborted. This is a finite-horizon lifetime criterion; 3000 s cannot see slow escapes (the simulator's no-burst escapes happen after 18,000 s). `summarize stable` writes `lambda_cap_bracket.json` with a bracket **per label** (`by_label`, incl. hardware); its `largest_all_stable_mult` is the window's upper edge together with max μ(n). Before the review E0b was a droppable cross-check (−8.70 GPU-h); it is now required because the simulator's measured from-empty λ_cap (2.41 ×) lies well below its curve peak (4.07 ×) and a window up to max μ(n) would predict "NOBURST good" at λ the simulator already calls unstable. The native pool needs its own E0b.

### Pre-registration (between E0a/E0b and E2, committed before any E2 job)
`configs/agentload_prereg_template.yaml` holds the predictions to be filled **by formula** from `mu_curve.json`, `calibration.json`, E0b's `lambda_cap_bracket.json` and the E2 config (`python -m analysis.prereg fill --template … --mu-curve … --calibration … --e0b-bracket … --out NEWFILE --lambda-mults … --rule "…" [--engine-cell-label L]`; refuses to overwrite; `validate FILE` exits 1 on errors):
- **recovery threshold = λ_miss** (sessions/s; FCFS μ(∞); simulator R4: 0.989): below it the closed curve never falls under the arrival rate, so any burst drains. **μ(300) is a recorded check only** (transient-biased, see Stage C);
- **metastable window (λ_miss, min(max_n μ(n), E0b's largest all-stable multiple × λ_miss))**: the good state exists and persists from empty over the run horizon, the all-miss tail cannot carry λ, a large enough burst traps. Above the upper edge the NOBURST arm may escape spontaneously or has no good state: those λ are not registered, and the NOBURST prediction is explicitly horizon-dependent;
- **trapped prefill-token rate** = E0a's all-miss uncached tokens/s (criterion (a) compares against it, ±15%); the trapped SESSION completion rate is informational only;
- **CAPPED drain**: `max_lambda = μ(n_cap) − 200 / (0.8 × (duration − t_b − end_window))`; λ above it is refused (the gate queue would not drain inside the run and kill condition 3 would fire for a reason unrelated to the mechanism);
- per-regime predictions for the three arms, the **PASS rule** and every analysis setting that changes a verdict (`trap_v2.*` incl. the estimator and the backlog metric, `windows.hit_metric`, `windows.cached_frac_threshold`, `windows.attribute_by`, `--fcfs-substr`), checked key by key against the applied analysis config (a test fails if a `trap_v2` key is neither registered nor exempt), the **kill conditions**, the λ points (`lambda_mults`, strictly inside the window with `boundary_margin_rel`, default 0.1; **the lead writes the rule that chooses them**) and the run protocol (duration, burst) read from the E2 config.
**Enforcement.** The E2 job (`MODE=burst`) calls `python -m analysis.prereg check-job FILE …` before the engine starts and refuses unless the file is valid, committed and clean and the job's `ENGINE_LABEL`, `MULTS`, `n_cap`, `CALIB_FILE` reference rates, hardware and protocol equal the registered ones; it exports the file's sha256 into every run's meta.json (`meta.prereg_sha256`). `summarize burst2 --prereg FILE` calls a verdict **decisive** only for the registered cell (`label == inputs.engine_cell_label` exactly, so `vllm-fcfs`, `sglang-fcfs-r0` and `-native` never count) at a registered λ inside the window, if the file is valid, committed and clean, and every run of the cell is bound to the file (sha256), launched under the registered protocol / references / cap / hardware, and started after the file's last commit; otherwise `kill_verdict_v2.json` says exploratory and lists each run's `registration_blockers`.

### E2: paired-arm burst test (the kill test)
`MODE=burst`, per (λ, seed) three arms with **common random numbers**: same seed ⇒ same Poisson arrivals and per-session specs (turn counts, tool times); the content salt is per run **within a job** (`RUN_IDX`; it keeps a missed flush from producing cross-run prefix hits in Stage C / E0a / E0b). With ONE arm per job, as every E2 arm must be, `RUN_IDX` restarts at 1 in each job, so all E2 arms have `content_salt = 1`: identical token content, not only identical lengths and timing. That is harmless (each job starts a fresh server) and tightens the pairing; the salts differ between arms only if several arms share a job (the three-arm default, which the wall-time check refuses in a 4 h job).
- **BURST**: as before (200 sessions in 60 s at t_b = 1200 s; 8700 s run).
- **NOBURST**: the same plan with the burst sessions removed (`arrivals.burst=null`; the post-burst window is still anchored at `arrivals.analysis_t_burst_s`, recorded in every arm).
- **CAPPED**: BURST plus a **client-side session cap** N_cap = argmax μ(n) from Stage C: the generator never has more than N_cap sessions active; excess new sessions wait in a FIFO gate between arrival and first request and their wait is logged.
One arm per job (`ARMS=burst|noburst|capped`; the default is all three, which the wall-time check refuses in a 4 h job). λ points: those of the filled pre-registration (`PREREG_FILE` is required), inside the measured window, × seeds {0,1,2} (budget: 3 λ). The engine is SGLang FCFS, refresh on (cell A). Between runs: cancel, drain, flush, canary-verify. **Native pool**: the same with `KV_TOKENS=native` for one λ (required item 2), after its own Stage C and E0b and under its own registration. **Grid** (cells A refresh off, B on/off, C, D): BURST arm only, λ points re-set from the pre-registration.

### Kill criterion v2 (pre-registrable) and PASS rule
Definitions are in §5. Per λ: **PASS** iff BURST **trapped** AND NOBURST **good** (hit > 0.8, outstanding backlog < 20) AND CAPPED **recovered**, in ≥ 2/3 of the seeds (≥ 3 seeds; a seed missing an arm counts as a failure). `kill_verdict_v2.json` lists per-seed arm states, pass counts, a plain-language diagnosis per λ (e.g. "the no-burst arm does not stay good (no good state at this λ)"), the pairing check (arm configs must differ only in the burst, gate, output, server-URL, content-salt and start-state keys; hardware and label must be equal), the legacy hit-rate verdict as secondary, the guard summary and the pre-registration provenance. Referee decision rule: if the NOBURST arm also collapses, or nothing traps, drop this framing.

The old rule ("the burst does not trap FCFS in ≥ 2/3 of runs at any λ ∈ (1.2, 2)×λ_miss ⇒ kill") survives as the SECONDARY hit-rate criterion in `kill_verdict.json` (`summarize burst`), computed over BURST-arm runs only.

| Outcome | Reading |
|---|---|

## 5. Analysis definitions (hit-rate rule = the sim's, now SECONDARY; throughput rule = primary)

Windows of 1000 s, complete windows only. Ported from `prefixmeta`: `trapped` = longest run of consecutive post-burst windows with hit rate < 0.2 lasts ≥ `trap_min_s`; `hit_eval` over [t_b + `hit_eval_from_s`, end]; `recovered` = `hit_eval` > 0.8 and tail-queue mean < 20 (tail = last min(5000, run/2) s); stable-from-empty; ramp escape (queue > 128) and re-entry (5 bins < 20). Additions: `good_before` (pre-burst hit > 0.5 and queue < 20); `trapped_aborted` (client aborted for overload and the last 3 post-burst windows all < 0.2); verdicts `recovered | trapped | trapped_aborted | indeterminate | no_burst`. The analysis defaults are the sim's (`trap_min_s` = `hit_eval_from_s` = 10000); the job scripts pass the short-protocol values (3000 / 4500).

**Throughput-based criterion (primary; `analysis/trap_v2.py`, parameters `trap_v2` in `configs/agentload_analysis.yaml`, copied into the pre-registration).** Per run, over the post-burst evaluation window W = [t_b + `eval_from_s`, end] (`eval_from_s` = 4500 s in the short protocol ⇒ W = 3000 s; shorter than 600 s ⇒ indeterminate), with λ the run's arrival rate and λ_miss the `arrivals.lambda_ref` it was set from (both recorded in `meta.json`):
- **backlog** = client sessions in the system (planned arrival minus completed/failed; **includes the gate queue and sessions asleep in tool time**); **slope** = OLS slope (sessions/s) of its 10 s bin means over W.
- **TRAPPED** iff (a) the **uncached prefill-token rate** over W (Σ (prompt − cached) tokens of the turns completing in W, per second) is within ±15% of E0a's all-miss rate (`arrivals.uncached_tokens_ref`) AND (b) slope > 0.5 × (λ − λ_miss); plus the explicit condition λ > λ_miss (without it the bare formula would call a healthy system at 0.9 λ_miss "trapped"). The session and turns-based completion rates are still written (`crit_a_sessions`, `crit_a_turns`, `estimators_agree`) and can be selected with `trap_v2.rate_estimator`.
- **DRAINING** iff slope < 0. **RECOVERED** (= "good") iff hit fraction > 0.8 and the **outstanding backlog** (requests in flight + sessions waiting at the client gate) < 20, both averaged over the last 300 s (`trap_v2.recovered_backlog_metric`; the sessions-in-system value is written as `backlog_end`). `state` ∈ trapped > recovered > draining > indeterminate. The old hit-rate verdict, hit_eval and the tail queue slope are carried next to it as secondary columns.
- **Why tokens, not sessions** (review finding 1; `experiments/agentload_trap_sim_traces.py`, recorded in `results/agentload_trap_sim_traces/20261021-070449`): in a trap with a growing backlog the sessions in progress are mostly early in their lives, and early turns have short prompts, so the all-miss session throughput runs ABOVE the closed-population λ_miss. On the simulator's own FCFS traps (84 trapped runs: 16 / 29 / 39 at λ = 1.5 / 2 / 2.5 × λ_miss; trapped = hit < 0.2 in every window of the span and at the end of the run), span [t_b + 5000, t_b + 8000):

| λ / λ_miss | trapped runs | sessions/s ÷ λ_miss (min-max) | (a) fires, sessions | turns/s ÷ E[T] ÷ λ_miss | (a) fires, turns | tokens/s ÷ all-miss (min-max) | (a) fires, tokens | (b) fires (conservation) |
|---|---|---|---|---|---|---|---|---|
| 1.5 | 16 | 1.17 (0.91-1.38) | 38% | 1.17 | 38% | 1.03 (1.00-1.04) | 100% | 69% |
| 2.0 | 29 | 1.34 (1.25-1.48) | 0% | 1.35 | 0% | 1.05 (1.04-1.07) | 100% | 100% |
| 2.5 | 39 | 1.52 (1.40-1.65) | 0% | 1.52 | 0% | 1.07 (1.06-1.08) | 100% | 100% |

  The spans [t_b+4000, +7000) and [t_b+10000, +13000) give the same picture (tokens: 100% everywhere; sessions: 50% / 0% / 0% and 38% / 3% / 0%). (b) was implied by (a)'s upper bound when (a) was in session units and λ ≥ 1.3 λ_miss; under the token band it is independent and weak at 1.5 × (69% of true traps), see O17. The token reference is the simulator's cache-off closed population 60 after 5000 s: 7337 prefill tokens/s; E0a on the real engine replaces it. A token-saturated draining run also satisfies (a): (b) (slope < 0) is what separates draining from trapped, as before.
- **Retracted:** the earlier "operating characteristic" (`experiments/agentload_trap_power.py`, P(a and b) = 0.91-0.93 at 1.6-1.9 ×) assumed Poisson departures at exactly λ_miss, i.e. it measured only the Poisson noise of a criterion assumed centred on λ_miss; the simulator's traps are not (1.17-1.52 × in sessions/s). The tests built on `tests/helpers_trap.py` have the same property (trapped service rate = λ_miss by construction): they check the logic, not realism. The script is kept as the noise floor of the session estimator only.

## 6. Deviations and open issues (for the lead)

- **D1: E2 timing (revised).** Sim: 5000 s warm-up + 25,000 s after the burst (30,000 s = 8.3 h; trap needs 10,000 s of hit < 0.2). The 4 h job limit cannot hold that, so the draft keeps t_b = 1200 s, 7500 s after (8700 s per run, one run per job), with the evaluation window starting at t_b + 4500 s (W = 3000 s). The first draft could not tell a trap from a slow drain by hit rate alone (draining a 200-session burst takes thousands of seconds); the **throughput criterion** (§5) is the answer to that: a drain shows a negative backlog slope and a completion rate above λ_miss, a trap a positive slope at ≈ λ_miss (tested on synthetic traces, including a slow drain that the old hit-rate rule calls "trapped"). What it cannot do is see an escape that happens after 8700 s (finite horizon, like the sim's λ_cap; the simulator's first no-burst escape is at 18,000 s, so the 8700 s NOBURST prediction is horizon-valid there). A literal-protocol alternative needs `--time` ≈ 8.5-9 h; its cost is in §7.
- **D2: λ_miss** from short runs and the turns-based estimator (sim: 100,000 s, 5 seeds).
- **D3: KV pool** capped at 300k tokens to match the sim (native ≈ 1M).
- **D4: context** > 32,768 needs the long-context override (UNVERIFIED), or `max_turns` 45.
- **D5: output feedback (pending Stage 0).** If an engine does not return output token ids, `synthetic` feedback makes every hit turn prefill Δ+d = 650 uncached tokens (about 18% more than the simulator's Δ = 550) and leaves a dead d-token branch in the KV pool per turn. Then BOTH engines must run `synthetic` (not one of each), and the simulator's λ_cap/λ_miss comparison is like-for-like only if the simulator is re-run with an effective Δ of 650 (not done here; it is the lead's call) or the deviation is reported next to D1-D4. `meta.json` records `output_feedback_configured` and `outcome.output_ids_source_counts`; calibration.json records `output_ids_sources`.
- **D6: from-empty premise.** `reset_and_verify` (canary prime, flush, canary check) runs before every run; the run's `meta.json` carries `start_state_verified` and the analysis marks unverified open-loop runs as an error-severity guard (`guards.json`, also copied into `kill_verdict.json`). Each run in a job also has its own `workload.content_salt` (`RUN_IDX`), so a missed flush cannot produce prefix hits across runs within a job (Stage C, E0a, E0b); E2 jobs hold one run each, so their salt is 1 and a fresh server per job provides the isolation; arrival and session-spec streams stay common across runs and engines. The canary needs the engine to report `cached_tokens` (else the check is `unverifiable` and `STRICT_FLUSH=1` aborts; MODE=smoke defaults to `STRICT_FLUSH=0` so Stage 0 can find out).
- **O1:** which cells count as "FCFS" for the kill rule. In the v2 design the pre-registered cell is SGLang FCFS with refresh on (label `sglang-fcfs-r1`). `--fcfs-substr fcfs` still selects the cells of the EXPLORATORY `kill_test_pass_rule_only`; a DECISIVE verdict needs `label == inputs.engine_cell_label` exactly (finding 4), so `vllm-fcfs` / `sglang-fcfs-r0` / `-native` cells are reported but never decisive under this registration.
- **O2 (superseded):** the E2 λ points are no longer fixed multiples (1.3/1.6/1.9×λ_miss): they come from the pre-registered window (λ_miss, min(max μ(n), E0b edge)), expressed as multiples of λ_ref, inside the CAPPED drain limit. 3 points are budgeted.
- **O3:** LPM patch (cell C). Not applied. In `python/sglang/srt/managers/schedule_policy.py` (path from the engine-sources note, no line number), change `WAITING_QUEUE_PREFIX_MATCH_MAX = 128` to a huge value (e.g. `10**9`). To be done in a separate editable install (`ENV_SGLANG_PATCHED`) so the stock cells stay stock. Whether prefix matching over thousands of waiting requests is too slow to serve is itself a finding.
- **O4:** the `a100` GRES may land on different A100 variants; the job scripts now `--exclude=nova22-amp-7` (unverified class), `calibration.json` records `hardware`, and cap/burst jobs refuse a different hardware string (`ALLOW_HW_MISMATCH=1` overrides; the analysis flags `hardware_mixed` / `hardware_vs_calibration`).
- **O5:** engine defaults I did not pin: HiCache off by default (per the engine-sources note), `radix_eviction_policy` lru. Confirm in the server log.
- **O6:** the vLLM FCFS cell cannot be varied (no ordering knob), only compared.
- **O7:** `/flush_cache` (SGLang) and `/reset_prefix_cache` (vLLM, may need `VLLM_SERVER_DEV_MODE`) are from memory; no flush = no "from empty".
- **O8:** the per-request client abort at 4000 in-flight requests. In the trapped regime the queue can reach thousands; a run that hits the cap is recorded as aborted, not as a failed experiment.
- **O9 (rate estimator; resolved).** The spec says "session completion rate"; the literal sessions/s is biased high in a trap (finding 1), so the default is now `uncached_tokens` and the sessions / turns-based estimators are secondary columns. The Stage-C argmax still uses `closed.mu_estimator` = sessions (one run per n; flagged when the runner-up is within 5%); `turns_based` has the same estimand and far lower variance but is also biased in the transient (+74% at n = 300 in the simulator window), so it was not switched. Registered in the pre-registration.
- **O10 (backlog < 20; revised).** The threshold 20 is the spec's. The simulator's quantity is the waiting queue + gate; the harness now compares the OUTSTANDING backlog (requests in flight + gated sessions; sessions asleep in tool time excluded). Sessions in the system were wrong for a saturated CAPPED arm (n_cap ≈ 24 admitted sessions can never be < 20). The outstanding backlog still includes the running requests (≤ 256 allowed, a few in a healthy state), so the engine waiting gauge would be closer if its metric name is confirmed in Stage 0; the healthy outstanding level at the registered λ is measurable in E0b's stable runs before registering.
- **O11 (hit > 0.8 has little headroom).** The turn-level hit fraction counts first turns as misses: ceiling ≈ 0.93 with E[T] = 14.76; with partial misses a healthy state can sit near 0.85. Both the follow-up-only and the token-weighted fractions are logged. The threshold is the spec's.
- **O12 (explicit λ > λ_miss in TRAPPED).** An addition to the spec's two conditions, see §5; it only matters for λ ≤ λ_miss.
- **O13 (CRN scope).** Arrivals and session specs are common across the three arms. Token content is common too, because one arm per job gives every arm `content_salt = 1` (only the multi-arm default would differ; finding 9). Pairing validity is checked from the effective configs: only `meta.arm`, the start-state record, the burst, the gate, the output dir, the server URL and the salt may differ; hardware and label may not (`pairing_problems` in the verdict).
- **O14 (Stage C has one run per n).** μ(n) noise is 5-10% (≈ 100-200 session completions in 1800 s); the argmax is flagged when ambiguous, but a wrong `n_cap` weakens the CAPPED arm, and the window edges inherit the noise (`boundary_margin_rel` in the template). Replicates at the knee (n = 24, 32) are the obvious extra spend (≈ 0.75 GPU-h per run plus startup).
- **O15 (ASSUMPTIONS in the budget, not in the spec).** (i) Stage C is repeated on the native pool (6.49 GPU-h) because the 300k-pool window does not transfer; (ii) **E0b is repeated on the native pool (9.22)** because the window's upper edge now depends on it (new in revision 3); (iii) the native-pool replicate is 1 λ × 3 seeds × 3 arms; (iv) E0b is REQUIRED (it was a droppable cross-check) and runs under FCFS; (v) grid cells D (vLLM) and C (patched LPM) have no Stage-C curve of their own, so their boundaries are not pre-registered; (vi) grid λ points are two of the pre-registered ones; if only one is in E2a, `E2b_sglang_fcfs_r1_2x` covers the other.
- **O16 (cost).** The paired kill test is 27 one-run jobs (75.82 GPU-h at 3 λ). Dropping to 2 λ saves 25.27; shortening the NOBURST arm would break the CRN pairing window and is not done.
- **O17 (OPEN DECISION for the lead: `slope_frac`).** With (a) in token units, (b) = slope > 0.5 (λ − λ_miss) is no longer implied by (a). On the simulator's traps (b) fires in 69% / 100% / 100% of the true traps at 1.5 / 2 / 2.5 ×, so (a and b) accepts 69% of true traps at 1.5 ×. I did not change `slope_frac`: tuning it on the simulator's own traces would be tuning on the answer. Options before registering: register only λ ≥ 2 × λ_miss (if inside the window), or choose a smaller `slope_frac` for a stated reason, or measure the young-session bias on the real engine first (E0b/E0a give the session rate of a trap-like all-miss state at open loop).
- **O18 (not implemented: staggered session ages in Stage C).** The review offered it as one of four fixes for finding 2; I took the cheapest (recovery threshold = λ_miss, μ(300) as a check). The transient also moves the n = 22-30 values (−9% to −25% in the simulator window), so `n_cap` and `mu_max` remain transient-affected; the CAPPED arm is robust to that only if μ(n_cap) > λ + drain margin (checked in the registration) and the argmax margin is read from `argmax_ambiguous`. Implementing staggered starts means session specs with a start turn and synthetic history in `workload.py`/`client.py`.
- **O19 (E0a population and warmup).** E0a runs a closed population of 32 with the same synchronised start; its warmup of 900 s is longer than the all-miss session lifetime at 32 (~675 s in the simulator), so its bias is small, but the token reference (`all_miss_uncached_tokens_per_s`) inherits whatever E0a's transient leaves; the population-64 check run is analysed separately.
- **O20 (unverified in the real engine).** That the trapped state's uncached-prefill rate sits within ±15% of the E0a all-miss rate is established on the simulator only (1.03-1.08 ×). The real engine's attention cost, radix-tree overhead and decode interleaving may shift it; the tolerance is registered before E2, so a miss would be a (reported) negative result about the criterion, not a tuning opportunity.
